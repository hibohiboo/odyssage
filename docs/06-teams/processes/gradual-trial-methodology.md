## 🎯 **段階的試行の核心理念**

### **基本原則**
```markdown
🔄 段階的試行による確実な成功:
✓ 小さな成功の積み重ね・確実性優先・リスク最小化
✓ 失敗時の即座停止・問題分析・学習・改善
✓ 一括処理・バッチ実行の完全回避・安全性確保
✓ 継続的学習・適応・品質向上・プロセス改善
```

### **成功の定義**
- **完全成功**: 全体完了ではなく、各段階の確実な成功
- **学習成功**: 失敗からの学習・改善・知識蓄積
- **プロセス成功**: 段階的実行プロセスの確立・習慣化
- **チーム成功**: 全担当の段階的試行による協働効率向上

## 🚨 **全担当共通の絶対原則**

### **絶対禁止事項（全役割適用）**
```markdown
❌ 複数タスク・複数ファイル・複数機能の同時実行
❌ 「まとめて」「一括」「全部」「同時」の発想・行動
❌ 失敗・エラーを無視した継続作業・推測作業
❌ 時間短縮・効率化を狙った安全手順の省略
❌ 未確認・未検証状態での次段階移行・作業継続
```

### **必須実行原則（全役割適用）**
```markdown
✅ 1つのタスク・1つのファイル・1つの機能のみ実行
✅ 完了・成功確認後のみ次タスク検討・実行
✅ 失敗・エラー・不明時の即座停止・分析・相談
✅ 環境確認・事前準備・安全手順の段階的実行
✅ 小さな成功体験の積み重ね・学習記録・改善
```

### **リーダー: 段階的チーム管理**

#### **チーム指示の段階的実行**
```markdown
🎯 1つの担当・1つの指示の原則:
1. 担当者選択: 1人の担当者に集中・複数同時指示回避
2. タスク明確化: 1つの具体的タスク・明確な完了基準
3. 完了確認: 担当者の完了報告・成果確認・品質確認
4. 次段階検討: 完了確認後のみ次タスク・次担当者検討
5. 課題対応: 問題発生時の即座サポート・個別支援

⚠️ 避けるべき行動:
❌ 複数担当への同時複雑指示・一括タスク配布
❌ 進捗未確認での追加タスク・次段階指示
❌ 問題発生時の放置・推測指示・無責任継続
```

#### **プロジェクト進行の段階的管理**
```markdown
📋 段階的プロジェクト推進:
- Phase管理: 1つのPhaseの完全完了確認後に次Phase
- 品質確認: 各段階での品質・整合性の1つずつ確認
- リスク管理: 早期発見・即座対応・影響最小化
- 学習記録: 成功パターン・課題・改善事項の記録・活用
```

### **設計担当: 段階的設計プロセス**

#### **設計文書の段階的作成**
```markdown
📝 1つの設計文書・1つの設計領域の原則:
1. 対象選択: 1つの設計文書・1つの設計領域に集中
2. 設計実行: アーキテクチャ・UI/UX・データ設計の個別実行
3. 検証確認: 実装可能性・技術制約・整合性の確認
4. レビュー依頼: 設計完成後の即座レビュー依頼・承認待機
5. 承認後移行: レビュー承認後のみ次設計検討・実行

⚠️ 設計時の注意事項:
❌ 複数設計文書の同時作成・一括設計
❌ 未検証・未確認状態での設計継続・拡張
❌ レビュー前の次設計開始・推測設計継続
```

### **実装担当: 段階的実装プロセス**

#### **ファイル・機能の段階的実装**
```markdown
💻 1つのファイル・1つの機能の原則:
1. ファイル選択: 1つのファイル・1つの機能に集中
2. 実装実行: TypeScript実装・型定義・基本機能実装
3. 静的確認: 保存・lint確認・TypeScript構文・import確認
4. 品質確認: StoryBook表示確認（人間依頼必要時）・コード品質確認
5. 完了後移行: 確認完了後のみ次ファイル検討・実装

⚠️ 実装時の注意事項:
❌ 複数ファイル・複数機能の同時実装・一括作業
❌ エラー・問題を無視した継続実装・推測実装
❌ 静的確認前の次ファイル実装・品質確認省略

🚨 重要制約: Claude CodeはSPA・ブラウザ確認不可
- UI動作・視覚確認が必要な場合は人間に依頼
- bun run dev起動・ブラウザ確認は無駄・実行不要
- StoryBook・実際の表示確認は人間との協働が必須
```

### **テスト担当: 段階的テスト実行**

#### **BDD/E2Eテストの段階的実行**
```markdown
🧪 1つのテスト・1つのFeatureの原則:
1. テスト選択: 1つのBDD Feature・1つのテストケースに集中
2. 環境確認: テスト実行環境・必要な前提条件の確認
3. テスト実行: 選択したテストのみ実行・結果詳細確認
4. 結果分析: 成功・失敗の詳細分析・問題特定・記録
5. 成功後移行: 成功確認後のみ次テスト検討・実行

⚠️ テスト時の注意事項:
❌ 複数テスト・複数Featureの同時実行・一括実行
❌ 失敗時の継続実行・問題無視・推測継続
❌ 環境確認省略・前提条件未確認でのテスト実行

🚨 重要制約: Claude CodeはUI動作・ブラウザ確認不可
- テスト実行結果の確認はClaude Code可能
- UI動作・ブラウザ状態の確認は人間に依頼
- テスト失敗時のブラウザ調査は人間との協働必須
```

## 🔄 **段階的実行サイクル（全担当共通）**

### **基本実行サイクル**
```markdown
🔄 段階的実行の5段階サイクル:

1. 📋 準備・計画段階
   - 開発環境確認・ツール準備・前提条件確認（Claude Code実行可能範囲）
   - 本日対象の1つのタスク・ファイル・機能選択
   - 実行手順・完了基準・失敗時対応・人間協働の確認

2. 🎯 実行段階
   - 選択した1つの対象のみ集中実行
   - 他タスク・他ファイルへの気移り完全回避
   - 丁寧・確実・急がない実行

3. ✅ 確認段階
   - 実行結果の詳細確認・品質確認・動作確認
   - エラー・警告・問題の有無確認
   - 完了基準達成の確実な確認

4. 📊 判断段階
   - 成功: 結果記録・次タスク検討・実行計画
   - 失敗: 即座停止・問題分析・解決方法検討
   - 不明: 即座相談・情報収集・支援要請

5. 🔄 次段階移行
   - 成功確認後のみ次タスク検討・選択・実行
   - 失敗解決後の同一タスク再実行・確認
   - 学習記録・改善事項の記録・共有
```

### **失敗時の即座対応プロセス**
```markdown
🚨 失敗・エラー発生時の5段階対応:

1. ⏹️ 即座停止
   - 追加作業・継続実行の完全停止
   - 他タスク・他ファイルへの移行禁止
   - 推測・試行錯誤の回避・安全確保

2. 📝 詳細記録
   - エラーメッセージ・問題状況の詳細記録
   - 実行手順・環境状況・前提条件の記録
   - スクリーンショット・ログファイルの保存

3. 🔍 問題分析
   - 1つの問題のみに集中・複数問題の同時分析回避
   - 根本原因・直接原因の特定・分析
   - 解決方法・代替手段の検討・評価

4. 💬 相談・支援
   - 15分ルール: 15分解決できない場合の即座相談
   - 担当領域・エスカレーション基準に基づく相談先選択
   - 具体的情報・詳細状況の正確な共有

5. 🔧 解決・再実行
   - 解決方法の実装・修正・環境調整
   - 同一タスクの慎重な再実行・確認
   - 成功確認後の学習記録・改善事項共有
```

## 🚨 **よくある失敗パターン・予防策**

### **典型的失敗パターン**
```markdown
❌ よくある段階的試行の失敗:

1. 「時間節約」の誘惑:
   - 「簡単だから一緒に」「まとめて効率的に」
   - 予防策: 効率性より確実性・安全性優先の意識

2. 「成功体験」による油断:
   - 「前回うまくいったから大丈夫」「慣れているから」
   - 予防策: 毎回の段階的確認・慢心回避・継続警戒

3. 「時間圧迫」でのプロセス省略:
   - 「急いでいるから確認省略」「とりあえず進める」
   - 予防策: 時間圧迫時こそ段階的実行・安全確保

4. 「問題軽視」による継続:
   - 「小さなエラーだから無視」「後で直せばいい」
   - 予防策: 即座停止・問題解決・安全第一の徹底
```

### **予防・対策手法**
```markdown
✅ 段階的試行の成功支援:

1. 環境整備:
   - チェックリスト・手順書・確認項目の整備
   - エスカレーション基準・相談先の明確化
   - 安全な実行環境・ツール・リソースの確保

2. 意識強化:
   - 段階的試行の価値・効果の継続的確認
   - 成功事例・効果的手法の共有・学習
   - リスク認識・安全意識の維持・強化

3. プロセス支援:
   - 段階的実行の具体的手順・フローの提供
   - 失敗時対応・エスカレーション手順の整備
   - 継続的改善・最適化プロセスの確立

4. チーム文化:
   - 段階的試行の価値共有・文化定着
   - 相談・支援の奨励・安全な環境整備
   - 学習・改善の重視・継続的成長促進
```
