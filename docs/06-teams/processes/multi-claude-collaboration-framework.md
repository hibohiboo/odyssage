# 複数ClaudeCode協働フレームワーク

## 📋 概要

**目的**: 複数のClaudeCodeセッションを活用した効率的な協働体制の確立  
**適用範囲**: Sprint 4以降の全開発フェーズ  
**策定日**: 2025-08-17  
**策定者**: Sprint 4 リーダー

## 🎯 フレームワークの価値

### 従来手法の課題
- 単一Claude内での複数役割管理による混乱
- Task機能の起動忘れ・役割境界の曖昧化
- 責任の不明確化・品質保証プロセスの混乱

### 新フレームワークの利点
- **明確な役割分離**: 各Claudeが専門役割に特化
- **追跡可能性**: 全ての判断過程がドキュメントで記録
- **品質向上**: 専門特化による深い検討・判断
- **並行作業**: 複数作業の同時進行可能
- **スケーラビリティ**: 新しい役割の容易な追加

## 🏗️ フレームワーク構成

### 基本原則
1. **1役割1Claude**: 各専門領域に専用ClaudeCodeセッション
2. **ドキュメントベース連携**: Claude間のやり取りは全てドキュメント化
3. **PO調整**: Claude間のメッセージ中継をPOが実施
4. **階層的意思決定**: 明確なエスカレーション・承認プロセス

### 標準役割定義

#### リーダー
**責務**:
- 全体方針・優先度決定
- 作業指示・品質承認
- 役割間調整・問題解決
- POへの報告・提案

**権限**:
- 作業指示書の発行
- 品質承認・却下判断
- 緊急時の方針変更
- リソース調整要求

#### 設計担当
**責務**:
- 要件分析・設計文書作成
- アーキテクチャ設計・技術選定
- 設計品質保証
- 実装仕様の詳細化

**権限**:
- 設計文書の作成・修正
- 技術選定の提案
- 設計レビューの実施
- 実装方針の策定

#### テスト担当
**責務**:
- BDD Feature作成・レビュー
- テスト戦略・計画策定
- 品質基準・受入れ基準定義
- テスト実行・結果分析

**権限**:
- テスト文書の作成・修正
- 品質基準の策定
- テストレビューの実施
- 品質問題の指摘

#### 実装担当（Phase 2以降）
**責務**:
- コード実装・技術実現
- 技術的課題解決
- パフォーマンス最適化
- 実装品質保証

**権限**:
- コードの作成・修正
- 技術的判断の実施
- 実装レビューの実施
- 技術課題の報告

## 🔄 運用プロセス

### 作業依頼フロー
1. **リーダーが作業指示書作成**
   - 適切なディレクトリに配置
   - POにファイルパス共有依頼

2. **POが担当Claudeにパス共有**
   - 新しいClaudeCodeセッション起動
   - 役割説明とファイルパス提供

3. **担当Claudeが作業実施**
   - 指示書に基づく作業実施
   - 作業報告書作成

4. **リーダーが品質確認**
   - 作業内容の確認・承認
   - 必要に応じて修正指示

### エスカレーション・意思決定
```markdown
## 意思決定階層

### レベル1: 担当Claude内判断
- 専門領域内の技術的判断
- 作業手順の詳細決定
- 成果物の品質調整

### レベル2: リーダー判断
- 役割間調整が必要な事項
- 作業範囲・期限の変更
- 品質基準の調整

### レベル3: PO判断
- 重要な方針変更
- 優先度・スコープの変更
- リソース・期限の大幅調整
```

### 緊急時対応
- **緊急度高**: POに直接相談
- **緊急度中**: リーダー経由で迅速対応
- **緊急度低**: 通常プロセスで対応

## 📊 効果測定・改善

### 週次振り返り指標
- **作業効率**: 計画vs実績時間
- **品質指標**: 修正回数・承認率
- **協働効率**: やり取り回数・意思決定速度

### 月次改善活動
- **プロセス最適化**: 非効率箇所の改善
- **テンプレート改良**: 実際の利用状況に基づく調整
- **役割定義調整**: 責務・権限の最適化

### 継続改善サイクル
1. **実施**: 新プロセスでの作業実行
2. **測定**: 効果・問題の定量把握
3. **分析**: 根本原因・改善点の特定
4. **改善**: プロセス・テンプレートの更新
