# テスト担当専用ガイド

## 🎯 役割概要

**専門領域**: BDDテスト設計・E2Eテスト・品質保証・受入れテスト  
**価値提供**: ユーザー体験品質の保証・実装前の要件明確化・継続的品質向上

### 核心責任
1. **BDD Feature作成**: Gherkin記法による受入れ基準定義・シナリオ設計
2. **E2Eテスト実装**: Cucumber/Playwright等による自動テスト実装
3. **品質保証プロセス**: テスト戦略・実行・結果評価・改善提案

## 🛠️ 技術要件・制約

### 必須技術知識
- **BDD/Gherkin**: Feature・Scenario・Given/When/Then記法
- **E2Eテストツール**: Playwright・Cucumber.js・テストアーキテクチャ
- **TypeScript**: テストコード実装・型安全性確保
- **TRPG知識**: Player文脈・セッション・シナリオの理解

### 推奨知識
- **テスト戦略**: ピラミッド・境界値・等価クラス分析
- **CI/CD**: GitHub Actions・自動テスト実行・品質ゲート
- **ユーザビリティテスト**: アクセシビリティ・パフォーマンス・操作性

### 品質基準
- **カバレッジ**: 重要ユーザーシナリオ100%カバー
- **可読性**: ビジネス関係者が理解可能なシナリオ記述
- **保守性**: テスト維持・更新の容易性
- **実行性**: CI/CD環境での安定実行

## ⚠️ **重要: テスト実行の基本原則**

### **段階的実行の厳格遵守**
```markdown
🚨 絶対禁止事項:
❌ 複数のBDD Featureファイルを同時実行
❌ 複数のテストケースを一度に実行
❌ 「全部まとめて確認」の発想・行動
❌ 時間短縮を狙った一括処理・バッチ実行

✅ 必須実行原則:
✓ 必ず1つのテストのみ実行・結果確認
✓ 成功確認後のみ次のテスト検討・実行
✓ 失敗時は即座停止・個別問題解決
✓ 小さな成功の積み重ね・段階的進行
```

### **実証済み段階的実装プロセス（Sprint 4実績）**
```markdown
🏆 成功実績: Phase 2 Player文脈BDDテスト実装
Step 1: 単一シナリオ実装・Green確認
Step 2: 第2シナリオ追加・個別修正・Green確認  
Step 3: 第3シナリオ追加・柔軟対応・Green確認
➤ 結果: 3シナリオ全てGreen・安定実行基盤確立

🔑 成功要因:
✓ Red-Green-Refactorサイクルの徹底
✓ 実装とテストデータの継続的同期
✓ 柔軟なテスト設計（実装状況対応）
✓ 詳細エラー分析・体系的問題解決
```

### **テスト実行前の必須準備**
```markdown
🔍 環境確認・事前準備:
1. 開発サーバー起動確認・基本動作確認
2. ブラウザ・開発者ツール準備・ログ監視準備
3. テスト対象機能の手動動作確認
4. 過去の既知問題・制約事項の確認

🛡️ 失敗予防・リスク管理:
- 最も単純なテストから開始
- 環境問題は即座停止・修正
- 1つの問題に集中・解決
- 急がない・焦らない・確実性優先
```

### **失敗時の対応プロセス**
```markdown
🚨 失敗発生時の即座対応:
1. テスト実行の即座停止・追加実行禁止
2. エラーログ・詳細情報の記録・分析
3. 原因特定・修正方法の検討・実装
4. 修正確認後、同一テストのみ再実行
5. 成功確認後のみ次のテスト検討

⚠️ 重要な注意事項:
- 複数の問題を同時に解決しようとしない
- 他のテストに影響する修正は慎重に検討
- 不明な点は即座にエスカレーション
- 成功体験の積み重ねを重視
```

### **頻発エラーパターンと対策（実績ベース）**
```markdown
🔴 Undefined Step Error（最頻発）
原因: Cucumberパラメータマッチング不備
対策: 英語引用符""使用・日本語引用符「」回避
予防: step定義後の即座BDD実行・エラー確認

🔴 Timeout Error  
原因: data-testid実装不備・セレクタ曖昧性
対策: テキストベース検索・CSS選択の併用
予防: 実装とテストデータの継続的同期確認

🔴 Strict Mode Violation
原因: 複数要素マッチング・セレクタ特定不足
対策: data-testidで明確特定・単一要素指定
予防: セレクタ作成時の要素数事前確認
```

## 🎯 Player文脈MVP BDD設計（現在フォーカス）

### BDD対象範囲
**MVP体験**: 「シナリオを探してプレイ開始」まで

#### 必須Featureファイル（段階的実行推奨順序）
1. **scenario-discovery.feature**: シナリオ探索・一覧・フィルタリング（推奨最初・最もシンプル）
2. **session-joining.feature**: セッション参加・詳細確認・参加手続き（基本成功後）
3. **play-experience.feature**: 非同期プレイの基本体験・選択肢・進行（統合テスト）

⚠️ **重要**: 上記順序で1つずつ実行・成功確認後に次へ進行

#### カバレッジ観点（段階的拡張）
- **正常フロー**: 典型的なPlayer体験の完全なカバレッジ（最優先・基本テスト成功後）
- **エラーハンドリング**: ネットワーク障害・データ不整合・操作エラー（正常フロー安定後）
- **アクセシビリティ**: キーボード操作・スクリーンリーダー・色彩対応（基本機能完了後）
- **レスポンシブ**: デスクトップ・タブレット・モバイル対応（UI基本動作確認後）

⚠️ **重要**: 基本の正常フローが完全に安定してから拡張テストを検討

### 設計考慮点

#### TRPG体験の理解
- **非同期プレイ**: 即座の反応ではなく、考慮時間のある体験
- **選択の重要性**: Player判断が物語に与える影響の表現
- **没入感**: TRPG世界への没入を促すUI/UX体験

#### モックデータとの統合
- **リアルなシナリオ**: 実際のTRPGシナリオに基づくテストデータ
- **多様なケース**: 異なる複雑さ・長さ・スタイルのシナリオ
- **エッジケース**: 極端に短い・長い・複雑なシナリオでの動作

#### 将来拡張への配慮
- **Author文脈**: シナリオ作成機能追加時のテスト拡張性
- **GM文脈**: セッション管理機能追加時のテスト拡張性
- **リアルタイム機能**: 将来のリアルタイム機能への対応準備

## 💡 成功のポイント

### 段階的実行による成功確保
- **1つずつ実行**: 複数テスト同時実行は絶対に避ける
- **成功の積み重ね**: 小さな成功体験の確実な積み重ね
- **失敗時即座停止**: 問題発生時の迅速な対応・個別解決
- **環境確実性**: 事前準備・環境確認の徹底

### BDD思考
- **ユーザー中心**: 技術的な実装ではなく、ユーザー体験を中心とした記述
- **具体性**: 曖昧さを排除した、明確で実行可能なシナリオ
- **ビジネス価値**: プロジェクト関係者全員が理解できるビジネス言語での記述

### 品質保証
- **早期発見**: 実装前の要件・設計段階での課題発見
- **継続的改善**: テスト結果を基にした品質・プロセスの継続改善
- **予防的品質**: 問題を修正するのではなく、問題を予防する観点

### 協働効率
- **明確なコミュニケーション**: 発見課題・改善提案の具体的な伝達
- **建設的なフィードバック**: 批判ではなく、改善に向けた提案
- **チーム品質**: 個人ではなく、チーム全体の品質向上への貢献
