# Odyssage プロジェクト テスト戦略

## 概要

本ドキュメントでは、Odyssageプロジェクトにおけるテスト戦略を定義します。
効率的で維持可能なテストアプローチを確立し、品質保証の指針とします。

## テスト戦略の基本方針

### 1. テストピラミッド構造

```
    E2E Tests (BDD)
       △ 少数・重要ユーザーシナリオのみ
      / \
     /   \
    /     \
   Integration Tests
  △ APIとデータベースの統合確認
 / \
/   \
Unit Tests
△ 個別機能・ロジックの詳細テスト
```

### 2. テスト種別と責務

#### Unit Tests（単体テスト）
- **対象**: 個別関数、コンポーネント、Hook
- **目的**: ロジックの正確性、エッジケースの検証
- **優先度**: 高（開発初期から実装）
- **実行頻度**: 開発中常時実行

#### Integration Tests（統合テスト）
- **対象**: API、データベース、外部サービス連携
- **目的**: システム間の連携確認
- **優先度**: 中（API完成後に実装）
- **実行頻度**: CI/CD時に実行

#### E2E Tests（エンドツーエンドテスト/BDD）
- **対象**: 重要なユーザーシナリオのみ
- **目的**: ビジネス価値の確認、リグレッション防止
- **優先度**: 低（機能完成後に実装）
- **実行頻度**: リリース前、定期実行

## 機能別テスト方針

### GraphDBシーン機能の場合

#### Phase 1: Unit Tests優先実装
```
1. バックエンドAPI関数の単体テスト
   - Neo4jクエリロジック
   - バリデーション処理
   - エラーハンドリング

2. フロントエンドHook・コンポーネントの単体テスト
   - データ取得Hook
   - 状態管理ロジック
   - フォームバリデーション
```

#### Phase 2: Integration Tests
```
1. APIエンドポイントの統合テスト
   - リクエスト/レスポンス検証
   - データベース連携確認
   - 認証・認可テスト

2. GraphDB・RDB間の整合性テスト
   - データ同期確認
   - 障害時の動作確認
```

#### Phase 3: E2E Tests（最小限）
```
1. 重要ユーザーシナリオのみ
   - シーン作成→表示の基本フロー
   - エラー時のユーザー体験確認
```

## テスト実装指針

### 1. 開発フローとテスト

```
開発段階          | 実装するテスト
------------------|------------------
設計・仕様策定    | テスト項目の洗い出し
実装開始          | Unit Test作成（出来るもの）
実装完了          | Unit Test完成・Integration Test作成
機能統合          | Integration Test実行・E2E Test検討
リリース準備      | E2E Test実装（必要な場合のみ）
```

### 2. テスト作成の優先順位

#### 高優先度（必須）
- ビジネスロジックのUnit Test
- APIエンドポイントのIntegration Test
- データベース操作のIntegration Test

#### 中優先度（推奨）
- UIコンポーネントのUnit Test
- フロントエンドHookのUnit Test
- エラーハンドリングのIntegration Test

#### 低優先度（必要に応じて）
- E2E Test（重要ユーザーシナリオのみ）
- パフォーマンステスト
- セキュリティテスト

### 3. 認証・環境に依存するテストの方針

#### Unit Tests
- **モック使用**: 外部依存をモック化
- **環境非依存**: ローカル環境で完全実行可能

#### Integration Tests
- **テスト環境使用**: 専用DB・API環境
- **データ分離**: テスト用データとプロダクションデータの分離

#### E2E Tests
- **最小限実装**: 認証・環境問題を避けるため最小限に留める
- **重要シナリオのみ**: ビジネス上重要な場合のみ実装

## ツール・フレームワーク

### 現在の技術スタック
- **Unit Test**: Vitest
- **Integration Test**: 現在使用中のtest framework
- **E2E Test**: Playwright + Cucumber（必要最小限）

### テストデータ管理
- **Unit Test**: テスト内でモックデータ作成
- **Integration Test**: テスト用DB・ファイクスチャ使用
- **E2E Test**: テスト環境での事前データセットアップ

## GraphDBシーン機能の推奨テスト計画

### 修正版テスト計画

#### 1. Unit Tests（優先実装）
```
バックエンド:
- GraphDB Neo4jクエリ関数のテスト
- シーンデータバリデーションのテスト
- エラーハンドリングロジックのテスト

フロントエンド:
- useGraphScenesQuery Hookのテスト
- シーン作成フォームのバリデーションテスト
- コンポーネントの状態管理テスト
```

#### 2. Integration Tests（第二優先）
```
API:
- GET /api/graph-scenes/scenario/{scenarioId} の統合テスト
- PUT /api/graph-scenes/{id} の統合テスト
- エラーレスポンス・認証の統合テスト

データベース:
- Neo4j・PostgreSQL間のデータ整合性テスト
- GraphDB障害時のフォールバック動作テスト
```

#### 3. E2E Tests（必要最小限）
```
重要シナリオのみ:
- シーン作成・編集・削除の基本フロー（1シナリオ）
- エラー時のユーザーメッセージ表示（1シナリオ）
```

## 今後の方針

### 短期的対応
1. **BDD E2Eテストの実装を一時停止**
2. **Unit Testから開始**: 実装済みの機能に対してUnit Test作成
3. **Integration Test**: APIの統合テストを優先実装

### 中長期的対応
1. テスト自動化・CI統合の強化
2. テストカバレッジ測定・改善
3. 必要に応じてE2Eテストの段階的追加

## 完了基準

### 機能開発完了の判定基準
```
✅ Unit Tests: 主要ロジックが85%以上のカバレッジ
✅ Integration Tests: 全APIエンドポイントが正常動作
✅ Lint・型チェック: エラーゼロ
✅ 手動動作確認: 基本ユーザーシナリオが正常動作
⭕ E2E Tests: 重要シナリオのみ（必須ではない）
```

この戦略により、効率的で持続可能なテストアプローチを実現します。
