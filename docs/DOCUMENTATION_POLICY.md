# Odyssage ドキュメント管理方針

## 基本理念

### ナレッジファースト
- **すべての設計判断を文書化**: 口頭での決定は必ず文書として記録
- **透明性の確保**: チーム内外からアクセス可能な形での情報公開
- **継続性の重視**: メンバー変更にも耐えうる知識の蓄積

### 実用性重視
- **3クリック原則**: 必要な情報に3クリック以内でアクセス可能
- **リビングドキュメント**: 実装と連動して自動更新される文書の活用
- **検索性**: Foam + VS Codeによる高速な情報検索

## ドキュメント体系

### 階層構造
```
docs/
├── 00-index.md                    # 全体インデックス（Foamハブ）
├── 01-getting-started/            # 新規参加者向け
├── 02-architecture/               # システム設計
├── 03-development/                # 開発プロセス
├── 04-deployment/                 # 運用・デプロイ
└── 05-archive/                    # 過去の記録
```

### ドキュメント分類

#### **Level 1: Core Documentation**
プロジェクトの中核となる必須ドキュメント
- `docs/03-development/process.md` (開発プロセス)
- `docs/02-architecture/database-design.md` (DB設計)
- `docs/01-getting-started/README.md` (プロジェクト概要)

#### **Level 2: Reference Documentation** 
実装者向けの詳細リファレンス
- API仕様書
- テスト戦略
- デプロイメント手順

#### **Level 3: Historical Documentation**
過去の判断記録・実装証跡
- スプリント実装記録
- 設計変更履歴
- 技術選定理由

## 作成・更新ルール

### 新規ドキュメント作成
1. **適切なディレクトリ配置**: 階層構造に従った配置
2. **命名規則遵守**: ケバブケース（`database-design.md`）
3. **テンプレート活用**: 後述のテンプレートを使用
4. **インデックス更新**: 作成時に親ディレクトリのREADME.md更新

### 更新・保守
- **リアルタイム更新**: 実装変更時の同期更新
- **リンク保守**: 月1回のリンク切れチェック
- **情報鮮度管理**: 四半期での古い情報レビュー

### バージョン管理
- **Git管理**: すべてのドキュメントをGitで管理
- **変更履歴**: コミットメッセージでの変更理由明記
- **ブランチ戦略**: 大幅変更時のfeatureブランチ活用

## Foam活用方針

### リンク戦略
- **WikiリンクFormat**: `[[ファイル名]]` 形式での相互参照
- **双方向リンク**: 関連ドキュメント間の相互リンク
- **コンテキストリンク**: 文脈に応じた自然なリンク配置

### タグシステム
```markdown
#architecture    # アーキテクチャ関連
#development     # 開発プロセス関連  
#deployment      # デプロイ・運用関連
#getting-started # 入門・概要関連
#archive         # 過去の記録
#decision        # 設計判断記録
#implementation  # 実装記録
```

### グラフビュー活用
- **知識マップ**: プロジェクト全体の知識構造可視化
- **関連探索**: 類似トピックの発見
- **孤立検出**: リンクされていない文書の特定

## 公開・共有方針

### 内部共有
- **Foam + VS Code**: 開発チーム内での日常的な知識管理
- **Git Repository**: バージョン管理された正式な記録

### 外部公開
- **GitHub Pages**: 設計判断・技術選定の透明性確保
- **静的サイト**: Astroによる読みやすい形での情報公開

### アクセス制御
- **パブリック情報**: 技術的な設計判断、学習内容
- **プライベート情報**: 個人情報、セキュリティ関連、商用機密

## 品質管理

### 文書品質基準
1. **正確性**: 実装との整合性
2. **完全性**: 必要な情報の網羅
3. **明確性**: 理解しやすい表現
4. **最新性**: 情報の鮮度維持

### レビュープロセス
- **ピアレビュー**: 重要文書の相互チェック
- **定期監査**: 四半期での情報鮮度確認
- **使用性評価**: 新規メンバーによる分かりやすさ評価

### メトリクス
- **アクセス効率**: 必要情報への到達時間
- **リンク密度**: ドキュメント間の相互参照度
- **更新頻度**: 情報の鮮度維持状況

## 📝 新規ドキュメント作成ルール詳細

### Phase 1: 事前企画・調査

#### 1.1 目的・対象読者の明確化
```markdown
# 必須検討項目
- 誰が読むのか？（開発者、新規参加者、運用担当者等）
- 何を解決するのか？（具体的な問題・課題）
- いつ使われるのか？（開発時、トラブル時、学習時等）
- どの程度の詳細さが必要か？（概要レベル、実装レベル等）
```

#### 1.2 既存文書との重複確認手順
```bash
# 1. 類似キーワードでの検索
ripgrep "キーワード" docs/ -i

# 2. タグ検索での関連文書確認
grep -r "#該当タグ" docs/

# 3. Foam Graph での視覚的確認
VS Code → Ctrl+Shift+P → "Foam: Show Graph"
```

#### 1.3 配置ディレクトリ選定基準
```markdown
# 判定フローチャート
新規参加者向け？ → 01-getting-started/
システム設計？   → 02-architecture/  
開発プロセス？   → 03-development/
運用・デプロイ？ → 04-deployment/
過去の記録？     → 05-archive/
```

### Phase 2: 文書設計・構造化

#### 2.1 ファイル命名チェックリスト
```markdown
✅ ケバブケース使用（例：`user-authentication-flow.md`）
✅ 英語または英数字のみ
✅ 拡張子は`.md`
✅ 長さは50文字以内
✅ 内容が推測できる名前
❌ スペース、アンダースコア、大文字使用禁止
❌ 一時的・非記述的な名前禁止
```

#### 2.2 文書構造テンプレート選択
```markdown
# アーキテクチャ設計書
- 概要・設計方針・詳細設計・実装ガイドライン

# 実装記録・証跡  
- 実装概要・技術的課題・完了項目・学習点

# プロセス・手順書
- 目的・前提条件・手順・トラブルシューティング

# API・技術仕様
- 概要・エンドポイント・パラメータ・レスポンス例
```

#### 2.3 必須コンテンツ要素
```markdown
# 全文書共通（必須）
1. 目的・対象読者の明示
2. 最低2つ以上の関連リンク  
3. 適切なタグ付与（3-5個）
4. 最終更新日または作成日

# 技術文書（推奨）
5. 前提条件・依存関係
6. 具体的な手順・コード例
7. トラブルシューティング情報
8. 関連外部リソース
```

### Phase 3: Foamリンク設計

#### 3.1 必須リンク配置ルール
```markdown
# 全ドキュメント必須
- [[../00-index]] - メインハブへの導線
- 上位階層README（[[../README]]または[[README]]）
- 関連する同階層ドキュメント（最低1つ）

# 技術文書推奨
- 実装ファイルへの参照
- 設計判断の根拠文書
- スプリント実装記録
```

#### 3.2 Wikiリンク記法ガイド
```markdown
# 基本形式
[[filename]]                    # 同ディレクトリ
[[subdirectory/filename]]       # 下位ディレクトリ  
[[../other-directory/filename]] # 他ディレクトリ

# 表示名カスタマイズ（推奨）
[[database-design|DB設計詳細]]
[[setup|環境構築手順]]

# 絶対パス（非推奨）
[[docs/02-architecture/api-design]] # ❌
```

#### 3.3 コンテキストリンク品質基準
```markdown
# ✅ Good Examples
データベース設計の詳細は [[../02-architecture/database-design|ハイブリッドDB構成]] で説明します。
環境構築が完了したら [[quick-start|開発を始める]] ことができます。

# ❌ Poor Examples  
[[database-design]] を参照。
詳細は [[setup]] 。
```

### Phase 4: 品質確認・統合

#### 4.1 作成前チェックリスト
```markdown
□ 重複確認完了
□ 適切なディレクトリ配置
□ 命名規則準拠
□ テンプレート使用
□ 必須要素記述
□ リンク設定完了
□ タグ付与完了
```

#### 4.2 品質確認項目
```markdown
# 内容品質
□ 情報の正確性
□ 読みやすさ・理解しやすさ
□ 完成度（TODO項目が残っていないか）
□ 対象読者への適切性

# 技術品質  
□ 全リンクの動作確認
□ コードブロックの動作確認
□ 画像・図表の表示確認
□ Foam拡張での正常表示
```

#### 4.3 統合作業
```markdown
1. 上位READMEへの追加
   - 該当ディレクトリのREADME.md更新
   - 適切なセクションに新文書リンク追加

2. メインインデックス検討
   - 重要度が高い場合は00-index.md更新
   - 目的別アクセスセクションへの追加

3. 関連文書の双方向リンク
   - 新文書から関連文書へのリンク
   - 関連文書から新文書への逆リンク
```

## 🔗 リンク保守ガイドライン詳細

### 日常メンテナンス（開発者個人）

#### リンク作成時の注意点
```markdown
# 推奨パターン
[[relative/path/filename]]      # 相対パス使用
[[filename|意味のある表示名]]    # 表示名で可読性向上

# 避けるべきパターン
[[/absolute/path/filename]]     # 絶対パス（移動時に破綻）
[[filename.md]]                 # 拡張子付き（Foam非推奨）
```

#### ファイル操作時の必須確認
```bash
# ファイル削除前（必須）
ripgrep "filename" docs/ --type md

# ファイル移動前（必須）  
ripgrep "\[\[.*filename" docs/ --type md

# 大規模リネーム前（必須）
find docs/ -name "*.md" -exec grep -l "old-name" {} \;
```

#### 新規作成時のリンク確認
```markdown
1. 作成直後
   - VS Code Foam拡張で表示確認
   - 設定したリンクの動作確認
   
2. 24時間以内
   - 関連文書からの逆リンク追加
   - 上位階層READMEの更新確認
```

### リンク切れ対応プロセス

#### 発見時の緊急対応（即時）
```bash
# Step 1: 影響範囲特定
ripgrep "broken-link" docs/ --type md -C 2

# Step 2: 原因調査
- ファイル削除？移動？リネーム？
- パス指定ミス？

# Step 3: 一時対応
- コメントアウト：<!-- [[broken-link]] -->
- 注釈追加：[[missing-link]] ※調査中
- 代替リンク：[[alternative-link|暫定的な代替]]
```

#### 根本解決（24時間以内）
```markdown
# 解決パターン別対応

## パターン1: ファイル移動・リネーム
- 正しいパスに更新：[[new/path/filename]]
- 一括置換で関連箇所更新

## パターン2: ファイル削除  
- 代替文書作成または
- 既存文書への統合または
- アーカイブ文書への参照

## パターン3: パス指定ミス
- 正しいパスに修正
- 再発防止のためのチェック強化
```
